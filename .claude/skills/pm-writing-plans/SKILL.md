# План блока

Скилл применяет исполнитель (`executor`). Спеку целиком пишет оркестратор; план каждого блока спеки пишешь ты сам, перед реализацией этого блока.

План - это решения, которые нельзя оставить на потом: какие файлы, имена и сигнатуры, значения из спеки, какие проверки доказывают каждую задачу. Его читают три стороны: ты после сброса контекста (работай по файлу, не по памяти), ревьюер (сверяет результат с намерением) и оркестратор.

## Правила

- Файл: `specs/<тема>/plan-<блок>.md`, рядом со спекой. Спека - источник истины, план - её аргумент. Один план на один блок, не на всю спеку.
- Сухо, технически, коротко. Больше самого блока спеки в разы = переписанный код: замени тела функций сигнатурами, именами проверок и ожидаемыми значениями.
- Не пересказывай то, что видно в проекте (структуру папок, код). Длинное выноси в отдельные файлы со ссылками.
- Самое важное (цель, ограничения) - в начале, риски для ревьюера - в конце.
- В примерах кода никаких пояснительных комментариев.
- Если блок зависит от прежних блоков, читай их планы и журнал: интерфейсы, которые они отдают, бери оттуда точными именами, не придумывай заново.
- Нужна установка инструмента: впиши строку "требуется согласие: установка X, зачем" и сразу остановись с `СТОП` (согласие даёт пользовательница через оркестратора), пока не получено.
- Ключи в плане не пишутся: "ключ X задаёт пользовательница вручную в .env".
- Проверка веба - во встроенном браузере: отдельный шаг с точными действиями и ожидаемым видом.
- Если блок слишком большой для одного плана, раздели на задачи; если спека блока настолько неясна, что любой путь - догадка, остановись с `СТОП`.

## Шапка

```
# <Тема>, блок <N>: план

**Спека:** specs/<тема>/spec.md, блок <N>
**Цель:** одно предложение.
**Подход:** 2-3 предложения.
**Стек:** ключевые технологии.

## Глобальные ограничения
Требования спеки на весь проект, дословно, по строке: версии, запреты, правила текста, платформа.

## Задачи
...

## На что смотреть ревьюеру
Пять входов или условий, которые спека подразумевает, но проверки задач не покрывают, самые вероятные первыми. Спека не перечисляет всё, с чем встретится программа, и её молчание не разрешает входу ломать программу. Для каждой строки добавь проверку в задачу, которой принадлежит код.
```

## Задача

```
### Задача N: <название>
**Файлы:** создать `путь`, изменить `путь:строки`, проверка `путь`
**Интерфейсы:**
- Берёт из прежних задач: точные сигнатуры
- Отдаёт следующим: точные имена, типы параметров и результата
**Критерий готовности:** ссылка на критерии приёмки блока спеки

- Шаг 1: написать падающую проверку (имя, что утверждает, точные значения из спеки)
- Шаг 2: запустить, убедиться, что падает. Ожидается: <сообщение>
- Шаг 3: реализовать `имя(параметры) -> результат` в `файл`
- Шаг 4: запустить, убедиться, что проходит. Ожидается: <результат>
```

Чекбоксы не ведутся: прогресс - только строки `Задача N: готова` в журнале `specs/<тема>/progress.md`. Коммит - отдельный шаг только если оркестратор передал просьбу пользовательницы о коммитах.

Размер задачи: наименьший кусок со своим циклом проверки, который имеет смысл принимать отдельно. Настройку и каркас складывай в задачу, которой они нужны. Делить там, где ревьюер мог бы отклонить одну задачу и принять соседнюю. Задача заканчивается проверяемым результатом.

Шаг однозначен, когда по нему можно написать ровно одно разумное решение. Дефекты: "TBD", "обработать крайние случаи", "добавить валидацию", "написать тесты на вышеописанное", функция без определения. Тело, уже определённое сигнатурой и проверками, - лишнее.

## Самопроверка (сам, без агента)

1. **Покрытие блока:** на каждый критерий приёмки и контрольный пример блока есть задача и проверка.
2. **Шаги:** каждый однозначен и без лишнего.
3. **Согласованность:** имена и типы в поздних задачах совпадают с ранними и с прежними блоками.
4. **Риски ревьюера:** каждый подтверждён проверкой.
5. **Пропорция:** план заметно длиннее блока спеки - сократи.

Исправляй сразу, без повторного ревью. Затем запиши в журнал в «Актуальное состояние»: `Блок N: план готов, начинаю задачу 1` и переходи к реализации под `pm-tdd`.
