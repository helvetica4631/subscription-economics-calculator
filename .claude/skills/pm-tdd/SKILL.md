# Разработка через проверки (TDD)

Сначала проверка. Смотришь, как она падает. Потом минимальный код, чтобы прошла. Если не видела падения, не знаешь, проверяет ли она нужное.

Нарушение буквы правила - нарушение смысла.

## Правила проекта

Скилл применяет исполнитель (`executor`). Общие запреты (комментарии, `.env`, 3 попытки, стоп-условия) описаны в его роли.

- Установка средства запуска проверок: нужна установка - остановись и верни оркестратору `СТОП`, согласие даёт пользовательница.
- Решение об исключениях (одноразовый прототип, сгенерированный код, настройки) принимай сам и записывай в журнал как `Решение`.
- Для веб-интерфейса и внешнего вида: логику проверяй автоматическими проверками, внешний вид и пользовательский сценарий - во встроенном браузере по критериям приёмки спеки. Не выдавай осмотр за автоматическую проверку и наоборот.

## Железное правило

```
НИКАКОГО КОДА ПРОДУКТА БЕЗ СНАЧАЛА ПАДАЮЩЕЙ ПРОВЕРКИ
```

Написала код раньше проверки: удали и начни заново. Не оставляй "для справки", не "подгоняй", не смотри. Удалить значит удалить.

## Красный - Зелёный - Улучшение

**КРАСНЫЙ.** Одна минимальная проверка, одно поведение, понятное имя, настоящий код без подмен, где возможно.

**Увидь красный (обязательно).** Запусти. Убедись: проверка *падает* (не ломается с ошибкой), сообщение ожидаемое, падает потому что функции нет, а не из-за опечатки. Прошла сразу: ты проверяешь существующее поведение, исправь проверку. Ошибка запуска: исправь и перезапусти.

**ЗЕЛЁНЫЙ.** Самый простой код, который проходит проверку. Не добавляй функции, не улучшай остальное.

**Увидь зелёный (обязательно).** Проверка проходит, остальные тоже, вывод без ошибок и предупреждений. Падает другая: чини сразу. "Остальные" - весь набор проверок проекта, а не только твой файл. Запусти общую команду проекта, даже если задача называла один файл. Любое падение, в том числе не твоё, называй в отчёте: красная проверка, пролетевшая мимо и не упомянутая, делает отчёт ложным.

**УЛУЧШЕНИЕ.** Только после зелёного: убрать дубли, улучшить имена, вынести общее. Зелёный остаётся, поведение не добавляется.

## Хорошие проверки

Каждая проверка называет поломку, которую ловит. Перед телом проверки ответь: какое изменение кода продукта её уронит, и это ошибка или решение?

- **Ожидаемое значение вычисляй вручную**, литералом. Не тем кодом, который проверяешь, и не его помощниками (зеркальная проверка всегда зелёная).
- **Не проверяй решения.** Если уронить проверку могут только намеренные решения (значение константы, формулировка сообщения, внутреннее устройство), она срабатывает на пересборку и спит при ошибках. Проверяй поведение, которое от решения зависит: не "лимит равен 5", а "после 5 неудач шестой попытки нет".
- **Поведение, не текст.** Не проверяй, что в файле есть строка. Запускай с заданными входами и сверяй результат, побочные эффекты, коды выхода.
- **Твой код, не чужая платформа.** Проверяй договорённости на границах своего кода. Тривиальные конструкторы и геттеры проверок не требуют.
- **Подмены.** Утверждение о подмене ничего не доказывает: проверяй реальный компонент или убери утверждение. Подменяй только медленное или внешнее, узнав все побочные эффекты настоящего. Подмена копирует полную структуру настоящих данных. Код только для проверок живёт в служебных файлах проверок, не в коде продукта. Подмена раздулась больше самой проверки: переходи на проверку с настоящими компонентами.
- Одна проверка - одно поведение. "И" в названии: раздели.

**Проверка мутациями перед завершением.** Мысленно испорть код (не та константа, не та ветка, нет побочного эффекта, пустой ответ, нет проверки пустого/нулевого/чужого ввода). На каждую порчу должна падать хотя бы одна проверка. Не падает ничего: поведение не защищено или проверка пустая.

## Исправление ошибок

Нашла ошибку: сначала проверка, воспроизводящая её. Красный - зелёный по циклу. Без проверки ошибки не исправляй. Пример: "пустая почта принимается" -> проверка "форма отклоняет пустую почту с сообщением" -> падает (получено: сообщения нет) -> минимальное условие -> проходит -> улучшение.

## Отговорки

| Мысль | Реальность |
|---|---|
| "Слишком просто для проверки" | Простое ломается. Проверка занимает минуту. |
| "Проверю потом" | Проверка после кода проходит сразу и ничего не доказывает. |
| "Уже проверила руками" | Ручная проверка не оставляет записи и не повторяется. |
| "Жалко удалять код" | Потраченное время уже потрачено. Код, которому нельзя верить, и есть потеря. |
| "Сначала разведаю" | Разведка - в одноразовый прототип, потом выбрось и начни с проверки. |
| "Трудно проверить" | Трудно проверить = трудно использовать. Упрости интерфейс. |
| "Нужно подменить всё" | Код слишком связан. Передавай зависимости снаружи. |

## Красные флаги: удалить и начать заново

Код раньше проверки; проверка прошла сразу; не можешь объяснить, почему упала; "потом допишу"; "только в этот раз"; "это другое".

## Чек-лист перед завершением

- У каждой новой функции есть проверка
- Каждую видела падающей, по ожидаемой причине
- Код минимальный
- Весь набор проходит, вывод без ошибок и предупреждений
- Крайние случаи и ошибки покрыты
- Подмен нет, кроме неизбежных
- Проверка мутациями сделана

Не отмечается всё: TDD пропущен, начни заново. Затем `pm-verification` перед любым заявлением о готовности.
